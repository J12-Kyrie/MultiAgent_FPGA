# 第三章 系统总体设计

## 3.1 系统架构概述

### 3.1.1 整体设计哲学

本框架的核心设计目标是构建一套通用的多智能体硬件设计自动化架构，使其适用于任何可分解为有向无环图（DAG）的多模块硬件设计任务。

本框架的核心设计哲学可概括为"框架控制"（Framework-controlled）原则，即批次推进决策、验证通过判定和状态机转移均由框架代码而非 LLM 本身掌握。这一原则与传统"提示词控制"（Prompt-controlled）方案形成根本性的对立：在提示词控制方案中，Agent 通过自然语言指令自行决定何时宣告完成、何时推进阶段，这不可避免地引入 LLM 幻觉和不收敛风险；而在本框架中，LLM 的角色严格限定为局部执行者——它生成或修复代码，但无权声明验证已通过或批次已完成。

框架控制的另一个维度体现在数据流的单向性：规格中间表示 → 有向无环图执行计划 → 工作区草稿 → L0/L1 验证 → 晋升 → 集成回归。每个阶段的进入条件由框架在文件系统层面检查，Agent 通过写文件向框架传递信息，框架通过门控回调决定是否推进。

### 3.1.2 六层架构

本框架采用六层分层架构，各层的设计均面向通用多模块硬件设计自动化，不依赖于特定设计对象。各层职责如表 3-1 所示。

**表 3-1: 六层架构职责一览**

| 层级 | 名称 | 职责 |
|------|------|------|
| 第一层 | Contract（合约层） | 定义全部数据模型，所有模型采用严格模式（禁止额外字段），构成系统第一道反幻觉屏障 |
| 第二层 | Synthesis（合成层） | 将设计蓝图实例化为规格中间表示、有向无环图执行计划和集成回归清单 |
| 第三层 | Execution（执行层） | 封装 Verilator 编译/仿真操作，实现 L0/L1/L2/集成回归四级执行器 |
| 第四层 | Runtime（运行时层） | 负责 SDK 集成、Agent 工厂、会话编排和门控驱动的批次执行 |
| 第五层 | Generation（生成层） | 管理工作区全生命周期：创建、草稿注入、修复循环和晋升 |
| 第六层 | Agent/Prompt（智能体/提示词层） | 定义角色规范、提示词合成和 Skill 注入策略 |

各层的详细设计将在第六章中展开阐述。

## 3.2 验证案例：AES-128 全系统设计分解

本节以 AES-128 加密全系统为具体实例，展示上述通用框架如何将一个多模块硬件设计分解为 DAG 结构并进行自动化验证。

### 3.2.1 模块依赖 DAG

本框架以 AES-128 加密全系统为案例，共包含 4 个硬件模块，其依赖关系构成一个有向无环图（DAG）。该 DAG 结构在蓝图加载器中以硬编码方式定义，并在有向无环图执行计划的模型验证器中通过深度优先搜索（DFS）进行无环验证。

![图 3-2: AES-128模块依赖DAG](../fpga_flow/diagrams/02_aes_node_dag.png)

4 个模块的角色与依赖关系如下：

- **aes_sbox**：S-box 字节替换（纯组合逻辑），DAG 叶节点，无上游依赖，l2_policy 为 skip。
- **aes_key_schedule_128**：密钥扩展，生成 11 组轮密钥，依赖 aes_sbox，criticality 为 high。
- **aes_round_transform**：单轮变换（SubBytes/ShiftRows/MixColumns/AddRoundKey），依赖 aes_sbox，criticality 为 high。
- **aes128_encrypt_core**：顶层加密核心，集成全部子模块，实现 11 周期延迟的握手接口，DAG sink 节点，l2_policy 为 required，criticality 为 high。

### 3.2.2 模块端口规范

**表 3-2: 4 模块端口规范一览表**

| 模块 | 信号名 | 方向 | 宽度 | 说明 |
|------|--------|------|------|------|
| aes_sbox | in_byte | input | 8 | 待替换的输入字节 |
| aes_sbox | out_byte | output | 8 | 替换后的输出字节 |
| aes_key_schedule_128 | key | input | 128 | AES-128 原始密钥 |
| aes_key_schedule_128 | round_keys | output | 1408 | 11 组轮密钥（11×128 bit） |
| aes_round_transform | state_in | input | 128 | 轮变换输入状态 |
| aes_round_transform | round_key | input | 128 | 本轮密钥 |
| aes_round_transform | is_last_round | input | 1 | 末轮标志（跳过 MixColumns） |
| aes_round_transform | state_out | output | 128 | 轮变换输出状态 |
| aes128_encrypt_core | clk | input | 1 | 时钟信号 |
| aes128_encrypt_core | rst | input | 1 | 同步复位（高有效） |
| aes128_encrypt_core | start | input | 1 | 加密启动握手信号 |
| aes128_encrypt_core | plaintext | input | 128 | 明文输入 |
| aes128_encrypt_core | key | input | 128 | 加密密钥 |
| aes128_encrypt_core | ciphertext | output | 128 | 密文输出 |
| aes128_encrypt_core | done | output | 1 | 完成单周期脉冲 |
| aes128_encrypt_core | busy | output | 1 | 运算进行中标志 |

上述接口规范在蓝图加载器中以端口规格字典形式定义，经合约编译器转换为模块合约模型，并写入各模块工作区，成为 Agent 在生成和修复过程中不得更改的冻结接口约束。

## 3.3 Agent 角色与 LLM 配置

### 3.3.1 Agent 角色体系

本框架共定义 3 种 Agent 角色，对应 5 个 Agent 构建函数。每个构建函数返回的智能体生成规格包含角色类型、LLM Profile、系统提示词、Skill 键集合、允许的编排器状态集合及可写路径约束。具体如下：

- **执行编排器**：使用快速执行模式，持有执行工具，允许在除终态之外的全部 9 个状态下活动，不持有任何可写路径（编排器不直接写文件）。
- **终态汇总编排器**：使用深度思考模式，持有完成工具，仅允许在集成就绪、集成回归和终态三个状态下活动，负责生成最终工作流报告。
- **单模块工作者**：使用快速执行模式，持有执行工具，可写路径严格限定为该节点的 RTL 文件和测试台文件，仅允许在模块设计、L0 和 L1 三个状态下活动。
- **专用修复工作者**：使用快速执行模式，不持有执行工具（修复阶段不允许触发执行），遵循"编辑优先"协议。
- **L2 测试活动代理**：使用快速执行模式，持有执行工具，仅允许在 L2 可选状态下活动，不允许 RTL 或测试台编辑。

### 3.3.2 双 LLM Profile 策略

系统定义两种 DeepSeek API 调用配置：

- **深度思考模式**（推理力度为中等）：计算成本较高但推理能力强，用于需要跨模块推理的编排器（规格分析、架构设计、集成回归阶段）以及最终汇总编排器。
- **快速执行模式**（推理力度为零）：响应快速、成本低，用于局部任务执行的工作者（模块生成、验证、修复、L2 测试）。

这一双 Profile 设计的核心逻辑是：跨模块决策（如判断模块间接口是否一致、决定是否升级）需要深度推理能力，而节点本地任务（如基于已有设计经验修复一个编译错误）不需要耗费推理资源，使用快速模式即可完成。通过在正确的任务上使用正确的 Profile，系统在保证决策质量的同时控制了 API 调用成本。

**表 3-3: Agent 角色-LLM Profile-工具矩阵**

| Agent 角色 | LLM Profile | 持有工具 | 典型活动状态 |
|-----------|-------------|---------|------------|
| 执行编排器（Workflow Orchestrator） | FAST | run_executor | MODULE_DESIGN / L0 / L1 |
| 终态编排器（Finalizer Orchestrator） | THINKING | FinishTool | INTEGRATION_READY / DONE |
| 模块工作者（Module Worker） | FAST | run_executor | MODULE_DESIGN / L0 / L1 |
| 修复工作者（Repair Worker） | FAST | 无 | MODULE_DESIGN / L0 / L1 |
| L2 测试代理（L2 Campaign） | FAST | run_executor | MODULE_L2_OPTIONAL |

## 3.4 DAG 拓扑批调度与并行执行

### 3.4.1 拓扑分层算法

DAG 拓扑批调度是本框架处理多模块硬件设计的通用机制——对于任何 DAG 可分解的设计，拓扑批次规划器均可自动计算拓扑层级和并行批次。以 AES-128 的 4 节点 DAG 为例，拓扑分层结果为：

- **第一批次（Layer 1）**：[aes_sbox]——无依赖，单独执行。
- **第二批次（Layer 2）**：[aes_key_schedule_128, aes_round_transform, aes128_encrypt_core]——在 aes_sbox 完成后，三个模块的依赖均已满足，理论上可并行委派执行。

批次任务被封装为委派批次计划，包含批次标识、阶段、最大子代理数（默认 5）和任务列表。

![图 3-3: 批次执行循环](../fpga_flow/diagrams/03_batch_execution_loop.png)

### 3.4.2 工作区生命周期状态机

每个节点的工作区存在独立的状态机，定义了 7 个状态：

- **缺失**：工作区尚未初始化
- **草稿就绪**：工作区已初始化、草稿文件已由设计知识库模块注入领域设计知识
- **已验证**：L0 编译和 L1 仿真均通过，所有必需检查点均为通过
- **已晋升**：已从草稿工作区晋升至规范 RTL/TB 路径
- **修复中**：验证失败，正在修复循环中（未超出预算）
- **已阻塞**：修复预算耗尽，需要人工介入或升级至思考型编排器
- **已失败**：发生不可恢复的错误

节点策略引擎根据当前工作区记录状态和验证结果决定下一个子代理工作模式（生成、验证、修复、L2 执行或集成）。这一决策逻辑完全在框架侧执行，LLM 无法直接影响工作区状态的推进。

## 3.5 关键支撑机制概述

### 3.5.1 结构化修复循环

当 L0 编译或 L1 仿真失败时，系统启动结构化修复循环，核心流程为三步：

1. **生成修复合约**：修复请求生成器将失败阶段、错误摘要和编辑指令写入工作区。
2. **Agent 编辑**：修复工作者读取修复合约，按照阶段约束对目标文件执行精确编辑。
3. **验证与重测**：系统通过 SHA-256 哈希验证文件确实发生了实质变化，随后重新触发 L0/L1 验证。

### 3.5.2 升级策略

当修复次数达到阈值（默认 2 次）或问题跨越模块边界、涉及状态机逻辑或接口不兼容时，控制权从快速模式的工作者升级至深度思考模式的编排器。升级后编排器携带完整失败上下文决定后续策略。升级判定的详细条件和决策逻辑将在第四章中展开。

## 3.6 创新点总结

本节对本文提出的三个核心创新点进行概括性总结，各创新点的详细设计与实验验证分别在第四章、第五章和第六章中展开。

![图3-4: 三个核心创新点关系架构](../fpga_flow/diagrams/17_core_innovations.png)

**创新点一：基于 10 状态编排状态机与执行策略的框架控制多智能体协作架构**

本文提出了编排状态机与执行策略相结合的框架控制架构，用于替代传统提示词控制方案中将控制权交给 LLM 自身的做法。编排状态机定义了从规格解析到集成验证通过的完整生命周期状态空间，执行策略将每个状态确定性地映射到 LLM 配置和子智能体策略，基于拓扑排序的批次规划器将任意 DAG 分解为可并行执行的批次层。该架构的核心价值在于将批次推进和验证判定等控制逻辑内化到框架代码中，LLM 仅作为局部执行者参与工作，从而从根本上消除了 LLM 幻觉对流程推进的干扰。该架构不依赖于特定硬件设计对象，可通过替换蓝图适配不同的多模块设计任务（详见第四章）。

**创新点二：L0 至 L1 至 L2 至 Integration 四层分级验证体系与检查点协议**

本文设计了面向通用多模块硬件设计的四层分级验证体系，覆盖从编译门控到系统级回归的完整验证链路。L0 编译门控在仿真前拦截语法错误，L1 进行单向量功能验证，L2 开展随机鲁棒测试，Integration 覆盖多场景系统级回归。检查点协议将验证意图编码为机器可解析的文本格式，由框架侧的检查点解析器自动判定验证结果，消除了 LLM 自行宣告验证通过的可能性。该验证体系具有设计无关性——任何硬件设计均可通过定义自身检查点列表接入，无需修改框架代码（详见第五章）。

**创新点三：驾驭引擎——六层约束引擎**

本文提出了驾驭引擎概念，将对不可靠 LLM 的约束工程从单一系统提示层扩展为技能、提示词、记忆、钩子、工具协议、命令体系六层结构化约束组合。其核心洞察是：在硬件设计这一高精度强约束领域中，单一系统提示层不足以可靠约束 LLM 行为，需要从多个维度形成多层防御矩阵，覆盖幻觉端口、语法错误、范围漂移、过度修改、格式错误等典型 LLM 失败模式。六层约束引擎的设计目标是在不依赖 LLM 自身判断力的前提下，通过结构性约束将 LLM 的行为限定在安全边界内（详见第六章）。

# 第四章 编排状态机与策略分层设计

编排状态机是本框架的核心控制机制，其设计面向通用的多模块硬件设计自动化流程。状态机定义的执行阶段（规格摄入→架构设计→规划→模块设计→分层验证→集成回归→终态）适用于任何 DAG 可分解的硬件设计任务。本章先阐述状态机的通用语义设计，再以 AES-128 验证案例展示各状态的具体实例化内容。

## 4.1 10 状态编排状态机

### 4.1.1 状态定义与语义

本框架的编排器状态机由编排器状态枚举完整定义，共包含 10 个状态。这 10 个状态不仅是系统执行阶段的语义标记，更是执行策略映射的索引键——每个状态精确决定了当前阶段应使用哪种 LLM 配置和哪种子代理委派策略。各状态的 LLM Profile 与子代理策略映射详见第三章表 3-3。以下说明各状态的语义与行为。

**（1）SPEC_INTAKE / ARCHITECTING / PLANNING（规格摄入、架构设计、规划）**

前三个状态由框架合成层独立执行，整个过程零 LLM 调用。SPEC_INTAKE 将设计目标解析为结构化规格中间表示；ARCHITECTING 生成计划有向无环图并验证无环性；PLANNING 生成集成回归清单并初始化脆弱性历史记录。三个状态的子代理策略均为禁止委派。

**（2）MODULE_DESIGN（模块设计）**

模块设计状态是 LLM 首次深度介入的状态。框架为每个节点创建工作区目录结构，生成模块合约、测试台合约和模块设计简报三份合约文件，并将来自技能文件的领域设计知识写入草稿 RTL 和测试台文件，工作区状态从 MISSING 转变为 DRAFT_READY。

**（3）MODULE_L0（编译门控）**

L0 状态执行 Verilator 编译，仅验证 RTL 文件的语法合法性和端口声明正确性，不进行仿真。其设计意图是快速失败：语法错误通常在秒级内发现，无需等待仿真完成。

**（4）MODULE_L1（仿真与 Checkpoint 验证）**

L1 状态执行完整的编译-仿真流程，通过检查点解析器解析仿真日志中的 `CHECKPOINT|<name>|PASS|<detail>` 协议行。只有所有必需 Checkpoint 均为 PASS 时，节点工作区状态才转变为 VALIDATED。

**（5）MODULE_L2_OPTIONAL（条件性鲁棒测试）**

L2 为可选状态，仅在节点的 L2 策略不为 skip 时触发。自适应规划器根据脆弱性历史选择测试 profile（rand_small、rand_large 或 edge_cases），以固定种子进行大量随机或边界向量测试，发现反例时写出反例文件和脆弱性摘要。

**（6）INTEGRATION_READY / INTEGRATION_REGRESSION / DONE（集成与终态）**

当所有节点达到 PROMOTED 状态后，集成就绪解析器检查依赖闭包完整性并选取集成顶层目标。集成回归执行器运行 baseline、back_to_back 和 mid_reset 三种 campaign 并汇总 Checkpoint 结果。全部通过后进入不可转移的终态 DONE，由终态编排器生成终态报告。

编排器的状态转移方法封装了所有成功路径的状态转移逻辑。状态机按严格线性顺序从 SPEC_INTAKE 推进至 MODULE_L1，此后根据节点的 L2 策略字段分支：策略为 skip 时直接进入 INTEGRATION_READY，策略为 conditional 或 required 时先进入 MODULE_L2_OPTIONAL 再转入 INTEGRATION_READY。完整的状态转移路径如图 4-1 所示。上述 10 个状态可按执行主体归纳为三类：前三状态由框架合成层独立执行，中间四状态是 LLM 深度介入的模块级执行阶段，末三状态回归框架控制。

## 4.2 执行策略分层

执行策略的设计是领域无关的——它将状态映射到 LLM 配置和子代理策略，这一映射机制适用于任何硬件设计自动化场景。具体的映射内容基于通用的任务复杂度分析：跨模块决策需要深度推理，节点本地执行需要快速响应。

### 4.2.1 策略模型设计

执行策略是一个 Pydantic 模型（同样使用 `extra='forbid'`），包含三个核心字段：

- 状态到 LLM 配置的映射
- 状态到子代理策略的映射
- 修复尝试阈值（默认 2，下限 1）

模型验证器强制要求两个映射字典必须覆盖全部 9 个活跃状态（DONE 状态不需要策略映射，因为它是终态）。这一完整性检查意味着系统永远不会出现"进入某个状态但找不到对应策略"的情况——若在系统初始化时发现缺失映射，将立即抛出验证错误阻止系统启动。

### 4.2.2 LLM Profile 分级的设计依据

LLM Profile 分级规则与 3.3.2 节一致，具体映射见表 4-1。

### 4.2.3 子代理策略三级控制

子代理策略枚举定义了三个级别的子代理委派控制：

**禁止委派**：编排器不得在当前状态下启动子代理。适用于需要编排器独占控制的阶段：规格/架构/规划（这三个阶段由框架合成层执行，LLM 参与度低，不需要子代理）以及集成就绪/集成回归（这两个阶段需要跨模块推理，委派给子代理会导致上下文分散）。

**允许模块工作者**：编排器可以将节点本地任务委派给模块工作者子代理。模块工作者的作用域严格限定：模块工作者构建函数返回的智能体生成规格中，可写路径约束仅包含该节点的 RTL 文件和测试台文件，允许状态集合仅包含模块设计、编译门控和仿真验证三个状态。这一双重约束（路径约束 + 状态约束）确保模块工作者无法越权修改其他模块的代码或执行集成级别的操作。

**允许 L2 测试代理**：编排器可以启动专用的 L2 测试活动子代理。L2 测试代理构建函数确保测试代理不持有 RTL/TB 可写路径，且持有的执行器工具在 L2 阶段不允许触发代码编辑操作。

## 4.3 升级策略设计

### 4.3.1 升级触发条件

升级触发条件详见 3.5.2 节。从触发性质的角度，可将升级场景归纳为两类：数量触发（修复尝试次数达到阈值，边际收益递减）和性质触发（检测到跨模块、状态机或接口问题，立即升级，因为这些问题无法由节点本地的模块工作者独立解决）。

### 4.3.2 修复预算管理

修复预算分配函数根据节点的集成角色字段分配差异化的修复预算：顶层或 sink 节点获得 3 次修复机会，其他节点（叶节点和支撑节点）获得 2 次机会。这一差异化预算设计的依据是：顶层加密核心是整个系统最复杂的模块，其 FSM 逻辑（IDLE→ROUND→DONE 三状态）涉及多个子模块的集成，修复时更容易需要多轮迭代。相比之下，aes_sbox 等叶节点逻辑简单，若 2 次修复后仍失败，说明问题已超出模块工作者的能力范围，升级至编排器处理更为合适。

这一有限预算机制与已有同类方案中 Debug Agent 的无限重试策略形成鲜明对比：无限重试在理论上提供了更多自我修复机会，但在实践中可能导致系统陷入无效循环（例如 Agent 每次修复都破坏了其他已通过的 Checkpoint），且没有收敛保证。有限预算确保了系统的终止性。

### 4.3.3 升级后的行为

升级发生后，框架将失败模块的完整上下文（修复合约、验证日志路径、已尝试的修复历史）附加到编排器会话的下一条消息中。思考型编排器在接收到升级信息后，可以采取以下几种策略之一：

- 重新分析错误，生成新的修复合约并重置修复计数
- 判断该模块为不可修复（BLOCKED 状态），记录失败并继续处理其他节点
- 判断问题为跨模块接口不兼容，触发对相关模块的联合修复

## 4.4 框架控制 vs Agent 控制

### 4.4.1 核心设计决策

"为什么不让 LLM 决定何时推进工作流状态？"这一问题是本框架最核心的设计决策点。LLM 在控制流场景中存在三种典型失败模式：提前宣告成功（基于局部信息的幻觉式乐观判断，误将非必需 Checkpoint 的 PASS 当作验证通过）、无限修复循环（反复修改同一段逻辑却无法触达根本原因，无外部预算限制时可无限持续）和范围漂移（修复时越界修改其他模块的接口定义，破坏系统其他部分）。这三种模式是所有 LLM 驱动的工程自动化系统面临的共性挑战，也是本框架将控制权收归框架层的根本原因。

### 4.4.2 框架控制进度合约的设计意图

框架控制进度合约是基础合约之一，其核心约束明确声明："框架而非 Agent 拥有批次推进和工作流完成的控制权"。这条约束被注入所有 Agent 角色的系统提示词，配合编排器禁止完成混入和仅当前批次混入，构建了三重语义锁定：控制权归属声明、行动禁止规则和批次边界约束。三重约束共同作用，确保即使在 LLM 产生错误乐观判断时，其输出也不会导致工作流状态的错误推进。

### 4.4.3 批次门控回调模式

会话运行器的批次门控执行方法实现了批次门控模式，这是框架控制架构的运行时实现。该方法接收当前会话、任务消息、一个批次门控回调函数以及超时和轮询间隔参数，返回批次运行摘要。其工作机制如下：
1. 向 Agent 会话发送当前批次任务消息，在独立线程中启动 Agent 对话循环
2. 主线程以 0.2 秒间隔轮询批次门控回调（该回调检查文件系统中的 artifact 是否满足批次完成条件）
3. 当批次门控返回 True 时，立即暂停 Agent 会话，不等待 Agent 自行结束
4. 若超过超时时间后门控仍未满足，强制暂停会话并记录超时状态

这一模式的关键特征是：**文件系统是 Agent 与框架之间的唯一通信通道**。Agent 通过写文件（生成 RTL、写出编辑收据、输出验证报告）向框架传递工作进度；框架通过读文件（检查工作区记录状态、解析编辑收据、校验 Checkpoint 汇总）判断批次是否完成。这种设计有两个重要优点：一是 Agent 的任何言辞性声明（"我已完成此模块"）不产生任何框架层面的效果；二是文件系统的持久性使得即使 Agent 会话意外终止，框架也能从 artifact 文件中恢复工作状态。

## 4.5 小结

本章阐述了 10 状态编排状态机与执行策略分层机制。核心贡献在于策略分层的运行时实现：每个状态作为策略索引键精确绑定 LLM 配置与子代理策略，通过框架控制进度合约、批次门控回调和有限修复预算确保控制权内聚于框架而非 LLM。状态语义、策略映射和控制权分配原则均不依赖于特定硬件设计对象，框架骨架可直接复用于其他 DAG 可分解的多模块设计。
